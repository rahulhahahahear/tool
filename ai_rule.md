## 📋 Rules for AI (Strict Line-by-Line Compliance)

### Rule 1: Strict Platform Segregation (`windows/` and `linux/`)
Any platform-specific scripts, configurations, and tools must live under their respective platform folder:
* Windows tools and orchestration live in `windows/` (e.g. `windows/scan_from_map/`).
* Linux tools and orchestration live in `linux/` (e.g. `linux/scan_from_map/`).
Never mix or place platform code directly in the root directory.

### Rule 2: Strict Tool Sandboxing & Isolation
Every individual tool must have its own sandbox folder within its platform directory (e.g., `windows/<tool_name>/` and `linux/<tool_name>/`).
All scripts, helper modules, caches, and outputs generated by a tool must stay within its dedicated folder to ensure clean modularity and easy maintenance.

### Rule 3: Self-Contained Tool Dependencies
Each tool folder must maintain its own `requirements.txt` documenting the exact Python packages it requires.

### Rule 4: Master Launcher Behavior (`main.py`)
`main.py` is the universal entry point. When executed:
1. It must ask the user to choose the operating system (`Windows` or `Linux`).
2. It must ask the user to choose the interface mode (`GUI` or `CLI`).
3. It must launch the requested environment cleanly based on the user's input.
It also supports direct CLI flags (e.g. `--os windows --mode gui`) for scripted runs.

### Rule 5: Dual Execution Capability
Every tool inside the hub must support two modes:
1. **Integrated Hub Execution:** Launchable from the Hub GUI or Hub CLI.
2. **Standalone Execution:** Launchable directly from its own subfolder.

### Rule 6: Tool Registration Requirement
When creating a new tool or updating an existing one:
1. Register it in `windows/app.py` & `windows/cli.py`.
2. Register it in `linux/app.py` & `linux/cli.py`.

### Rule 7: Mandatory User Permission for Exceptions
The AI is strictly forbidden from bypassing, modifying, or creating exceptions to these rules without first asking and receiving explicit confirmation from the user.
